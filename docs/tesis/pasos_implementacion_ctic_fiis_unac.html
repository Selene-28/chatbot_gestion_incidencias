1. Tipo de investigación y diseño

El trabajo es una investigación aplicada. El diseño es pre-experimental con pre-test y post-test: se miden indicadores de la gestión de incidencias antes de introducir el chatbot y después de su uso, en la comunidad de la Facultad de Ingeniería Industrial y de Sistemas (docentes, personal administrativo y estudiantes). No hay grupo de control aleatorizado; el contraste es temporal sobre el mismo contexto institucional.

La duración de desarrollo prevista fue de seis semanas. Las fuentes de requerimientos son el planteamiento del problema y el Documento de Requerimientos Técnicos y Funcionales (DRS). Los PRD del repositorio normalizan el DRS con identificadores trazables (RF, RN, QA, API, F, ADR) y se actualizan si la implementación se desvía: son la especificación viva, no un anexo estático posterior al código.

La definición de terminado del software coincide con los once criterios de aceptación del DRS (QA-01 a QA-11). La suite e2e/ es el gate de release: el sistema se considera completo cuando esos criterios pasan de forma automatizada contra el stack real (nginx + APIs + MySQL + widget).

2. Problema, solución y objetivos (KPIs)

2.1 Problema

El CTIC de la FIIS-UNAC gestiona incidencias tecnológicas mediante el Sistema de Tickets CTIC, único canal oficial de soporte. Toda consulta —incluso las repetitivas y de baja complejidad (recuperación de contraseñas, acceso a plataformas, horarios, configuración de cuentas)— debe atravesar el mismo proceso de registro, clasificación, asignación y atención. Ello genera demora en la respuesta, acumulación de casos pendientes, sobrecarga del personal técnico con consultas que podrían autoservirse, dificultad para priorizar incidencias que sí requieren intervención especializada, y ausencia de atención fuera del horario de oficina.

2.2 Solución implementada

Un asistente virtual (chatbot) basado en inteligencia artificial, desplegado como widget web en el sitio institucional, que: (1) resuelve consultas frecuentes en lenguaje natural consultando una base de conocimiento institucional (arquitectura RAG), sin generar tickets innecesarios; (2) registra incidencias mediante un flujo guiado que valida datos y genera un ticket con código único (INC-AAAA-NNNN); (3) consulta el estado de tickets existentes por número o por correo; (4) ejecuta diagnósticos básicos guiados (WiFi, aula virtual, software y correo institucional); (5) escala al personal humano (handoff) cuando no puede resolver, adjuntando el contexto de la conversación; y (6) mide la satisfacción (encuesta 1–5) y registra métricas para la evaluación pre/post-test.

El enfoque conversacional es híbrido. Las operaciones críticas (registrar, consultar, escalar, encuesta) son máquinas de estado con botones, 100 % predecibles (QA-11). El LLM solo clasifica intención de texto libre y redacta respuestas FAQ ancladas a artículos. El modelo nunca ejecuta acciones transaccionales.

3.4 Restricciones y supuestos

El sistema de tickets real de la universidad es PHP + MySQL + Apache (XAMPP). Por ello la base de datos del proyecto es MySQL 8 y la integración se hace por API REST, agnóstica del lenguaje del otro lado. El presupuesto de tesis es reducido: los embeddings son locales (sin costo por consulta); el único costo variable es la API del LLM, acotada por diseño (capa de reglas, umbral RAG y modo degradado). La producción se asume en un servidor Linux universitario con Docker. Cuando el Sistema de Tickets CTIC real exponga API-01 a API-03 (o un adaptador sobre su MySQL), el chatbot se reconecta cambiando TICKETS_API_BASE_URL; no requiere cambios de código.

6. Arquitectura C4 y recorrido de un mensaje

6.1 Vista de contexto (C4 nivel 1)

Los actores son el usuario final (docente, administrativo o estudiante), el agente/técnico CTIC y el administrador CTIC. El sistema es el Chatbot de Gestión de Incidencias. Los sistemas externos son: la API de Claude (clasificación y redacción RAG), el Sistema de Tickets CTIC real (PHP/MySQL, integración futura por API-01 a API-03) y el sitio web institucional FIIS-UNAC, que incrusta el widget mediante un snippet JavaScript.

6.2 Vista de contenedores (C4 nivel 2)

En el navegador conviven el widget (burbuja flotante) y el panel de agentes. En el servidor, Nginx es el único punto de entrada. chatbot-api orquesta diálogo, router, RAG, handoff y métricas, y es el único componente que llama al LLM. ticket-service implementa el dominio de tickets y el panel, y simula el sistema real. MySQL guarda chatbot_db y tickets_db. Chroma vive embebido en chatbot-api. Los adjuntos se almacenan en un volumen fuera del árbol web.

6.3 Recorrido de un mensaje (vista dinámica)

Cuando el usuario envía un texto o pulsa un botón, el recorrido es el siguiente:

  • 1. El widget hace POST /api/chat/mensajes con sessionId y texto u opcionId, header X-Session-Token.
  • 2. Nginx reenvía a chatbot-api. Se persiste el mensaje del usuario (RF-09) con marca de tiempo.
  • 3. Si estado_bot = PAUSED (handoff activo), el mensaje se reenvía al agente y el motor de intenciones no responde (RN-05).
  • 4. Si hay flujo_activo (por ejemplo, registrando incidencia), el Dialog Manager procesa el paso; si la entrada es inválida, re-solicita (máximo 3 intentos → fallback). En el paso final de registro llama POST /api/incidencias (API-01) al ticket-service.
  • 5. Si no hay flujo activo y hay opcionId de menú, se inicia el flujo correspondiente.
  • 6. Si es texto libre, el router capa 1 (reglas, regex, keywords, etiquetas) intenta clasificar. Si no hay match, capa 2 (LLM con structured output). Confianza menor a 0,55 se trata como no_comprendida.
  • 7. Intent de flujo → se inicia la máquina de estados. Intent RAG → embedding local, búsqueda top-k en Chroma, generación anclada con Claude (streaming) o artículo textual en modo degradado. Intent de diagnóstico → árbol F-05. Social → texto fijo del DRS. fuera_de_alcance → mensaje LF-01. no_comprendida → fallback F-09.
  • 8. Se guarda la respuesta del bot con intent, confianza y latencia_ms. El widget pinta texto, botones, adjunto, encuesta o banner de handoff.

Nota. Única excepción documentada a ADR-03: la vista SQL v_autoservicio_diario hace un JOIN lógico entre conversaciones y tickets por código, solo para el KPI de autoservicio. El resto del tráfico chatbot → tickets es HTTP.

7. Decisiones de arquitectura (ADR-01 a ADR-08)

ADR

Decisión

Razón principal y alternativas descartadas

ADR-01

Híbrido: flujos deterministas + LLM/RAG

QA-11 exige happy paths correctos; LF-06 prohíbe respuestas no verificadas; baja el costo. Descartados: solo reglas (no cumple IA/NLP del DRS); solo LLM con tools (impredecible); Rasa; Dialogflow (lógica fuera del servidor universitario).

ADR-02

Python 3.12 + FastAPI en ambos servicios

Ecosistema NLP/RAG, async nativo para SSE, OpenAPI, Pydantic = SEG-04. La frontera con el PHP universitario es siempre REST/JSON.

ADR-03

ticket-service separado que simula el sistema real

Sin acceso al sistema real durante la tesis. chatbot-api nunca lee tickets_db; consume TICKETS_API_BASE_URL. Pasar a producción = cambiar la URL.

ADR-04

MySQL 8 como única BD relacional

Paridad con el stack de la universidad; JSON nativo; conocimiento local del CTIC.

ADR-05

Embeddings locales + Chroma embebido

Anthropic no ofrece embeddings; un proveedor de pago es innecesario para un corpus pequeño. Default: multilingual-e5-small. Si el corpus creciera a decenas de miles, migrar a Qdrant/Chroma server.

ADR-06

LLM Claude, modelos configurables

Desempeño en español, structured outputs, streaming. LLM_MODEL y LLM_MODEL_ROUTER independientes. Sin clave sk-ant- el sistema opera degradado de forma correcta.

ADR-07

Todo el sistema en contenedores Docker

Despliegue reproducible, aislamiento del XAMPP existente, rollback por imagen. Descartados: instalación nativa; Kubernetes (desproporcionado); PaaS externo para producción (Ley 29733: datos de la comunidad fuera de la institución).

ADR-08

Widget ↔ backend: REST + SSE

POST para enviar; SSE para primer token RAG y push del agente. WebSockets se descartó por complejidad en proxies universitarios.

12. Flujos conversacionales (F-01 a F-09)

El diálogo es una máquina de estados por conversación. Si no hay flujo_activo, el mensaje pasa al router (prd/06).

12.1 F-01 · Enrutamiento general

Mensaje entrante → si PAUSED, reenviar al agente. Si ACTIVE y hay flujo_activo, el Dialog Manager valida el paso (sí: avanza; no: re-solicita, máx. 3 → F-09). Sin flujo: si hay opcionId de menú se inicia el flujo; si no, el router. Según el intent: flujo, RAG, diagnóstico, social, fuera_de_alcance o fallback.

12.2 F-02 · Registrar incidencia (happy path del DRS)

Estados: identificacion → categoria → descripcion → prioridad → adjunto → confirmacion → creado. Pasos: (1) botón o intent «Registrar incidencia»; (2) nombre y correo si la sesión no está identificada; (3) validar @unac.edu.pe (QA-06); (4) escuela Industrial/Sistemas; (5) categoría desde tabla categorias; (6) descripción 10–2000; (7) prioridad Baja/Media/Alta (default Media); (8) evidencia opcional; (9) resumen con Confirmar / Corregir / Cancelar; (10) POST /api/incidencias con Idempotency-Key; (11) confirmación con código INC-AAAA-NNNN; (12) menú o encuesta.

En Corregir, el bot pregunta qué campo cambiar y vuelve a confirmacion. En Cancelar, descarta flujo_contexto y vuelve al menú. Si ticket-service falla: disculpa + Reintentar; los datos capturados no se pierden (REN-02, REN-05).

12.3 F-03 · Consultar estado

Si la sesión no tiene correo, se solicita. Luego: por número (formato INC-AAAA-NNNN) o por correo (hasta 10 tickets como botones). 200 muestra estado, categoría, fecha, técnico y última actualización. 403: «El ticket no pertenece a este correo» (sin revelar datos). 404: no encontrado + reintentar.

12.4 F-04 · Preguntas frecuentes (RAG)

Embedding de la consulta → top-k = 4 en Chroma. Si el score máximo supera el umbral (RAG_UMBRAL_SIMILITUD = 0,83, calibrado para e5-small: relevantes ≈ 0,88–0,92, irrelevantes ≈ 0,75–0,82), se genera respuesta anclada (streaming) o se muestra el artículo textual en modo degradado. Si no hay evidencia: «No tengo información sobre eso en mi base de conocimiento» y se ofrece registrar incidencia (QA-03).

Nota. El PRD 06 menciona un umbral de similitud coseno de 0,45 como punto de partida genérico. En la implementación con multilingual-e5-small el umbral operativo es 0,83; si se cambia el modelo de embeddings hay que recalibrar midiendo ambos grupos (verificación en e2e/test_qa03_faq.py).

12.5 F-05 · Diagnóstico básico guiado

Árboles estáticos versionados (no LLM), uno por categoría. Ejemplo WiFi: ¿WiFi o cable? → ¿ve la red UNAC? → ¿autentica pero no navega? → pasos (activar WiFi, portal cautivo, renovar IP, credenciales). Cada rama termina en «¿Se resolvió?». Sí: cierre + encuesta. No: F-02 pre-llenado con ubicación, tipo de conexión y síntoma. Aula Virtual, software y correo siguen el mismo patrón; sus pasos provienen de artículos KB de categoría diagnóstico.

12.6 F-06 · Escalar incidencia

Solicita número de ticket (o lo toma del contexto), motivo (10–500 caracteres) y llama PUT /api/incidencias/escalar validando propiedad por correo. Confirmación oficial de derivación. Ticket inexistente → reintento; Resuelto/Cerrado → explica y ofrece registrar uno nuevo.

12.7 F-07 · Handoff a agente humano

Disparadores: tres fallbacks, botón «Contactar con soporte», o diagnóstico fallido con usuario que pide humano. El bot muestra el texto de transición, pasa a PAUSED, crea handoff(pendiente) con los últimos 20 mensajes. El agente pulsa Atender → atendido; el chat es bidireccional por SSE (emisor agente). Al Cerrar: handoff cerrado, bot ACTIVE, encuesta F-08. Si nadie atiende en 10 minutos: expirado, disculpa y oferta de registrar incidencia asíncrona.

12.8 F-08 · Encuesta de satisfacción

Disparadores: cierre de handoff, ticket registrado + despedida, FAQ resuelta + despedida, intent finalizar. Botones ⭐1–⭐5 y comentario opcional u Omitir. POST /api/encuesta con ticketId o conversacionCodigo. Una vez por atención (RN-04); si se ignora, la conversación cierra igual.

12.9 F-09 · Fallback

«No comprendido» = intent no_comprendida, confianza < 0,55, o tres entradas inválidas en un paso de flujo. El contador fallback_consecutivos vive en conversaciones y se reinicia con cualquier mensaje procesado con éxito. Primer fallo: texto oficial 1. Segundo: texto 2 + menú fijo. Tercero: protocolo F-07.

13. Motor de IA: router de dos capas y RAG

Principio rector (ADR-01): el LLM nunca ejecuta acciones. Sus dos únicos trabajos son clasificar la intención de texto libre y redactar respuestas FAQ ancladas a artículos.

13.1 Router capa 1 — reglas

Gratis, menos de 5 ms, resuelve la mayoría de casos. opcionId de botón → intent directo. Diccionario de patrones: regex y keywords normalizadas (minúsculas, sin tildes). Ejemplos: consultar_estado reconoce INC-\d{4}-\d{4}, «estado de mi ticket», «mi incidencia»; saludo: «hola», «buenos días»; recuperar_correo: «contraseña» + «correo». Las etiquetas de kb_articulos pueden enrutar directo a RAG con el artículo como candidato prioritario.

13.2 Router capa 2 — clasificador LLM

Solo si la capa 1 no decide. Llamada corta a Claude con structured outputs (JSON válido, enum de los 16 intents). El prompt de sistema restringe el dominio a soporte tecnológico universitario; fuera de dominio → fuera_de_alcance; ininteligible → no_comprendida. Incluye los últimos tres turnos. Confianza < 0,55 → no_comprendida. Presupuesto típico: ~300 tokens de entrada / ~20 de salida. Modelo: LLM_MODEL_ROUTER (Haiku por defecto).

13.3 Recuperación RAG

Embedding local de la consulta; búsqueda en Chroma top_k = 4 con filtro activo = true. Re-ranking simple: bonus si las etiquetas aparecen en la consulta. Chunking: artículos ≤ 400 tokens se indexan completos; mayores se dividen por secciones (~300 tokens, solape 50) manteniendo articulo_id. Al crear/editar/desactivar se hace upsert/delete incremental. El comando reindex reconstruye el índice desde kb_articulos (idempotente).

13.4 Prompt de generación (reglas RN-07, RN-08, LF-05 a LF-09)

El asistente responde en español, claro y formal, solo con la información de los artículos proporcionados. Si no está en ellos, declara que no tiene esa información y ofrece registrar incidencia. Instrucciones paso a paso cuando corresponda. Nunca revela contraseñas ni datos de terceros. No atiende temas ajenos al CTIC. Máximo 150 palabras; listas numeradas sí, encabezados markdown no. La respuesta guarda fuentesKb (IDs) para auditoría de fundamentación.

16. Widget web

JS/CSS vanilla (ES2020), IIFE, sin frameworks ni variables globales. Clases con prefijo cbctic-. Paleta institucional: azul #1e3a5f, blanco, acento ámbar #e8a020. Se embebe con una línea: script src=…/widget/widget.js data-api=…/api. widget.js inyecta widget.css. Desktop 380×560 px; móvil <480 px a pantalla completa. Sesión en sessionStorage (no localStorage) porque el chat es efímero (timeout 15 min) y así no persisten datos personales entre pestañas. Todo el contenido del servidor se pinta con textContent (nunca innerHTML), en línea con SEG-04. Área de mensajes con role=log y aria-live=polite.

Tipos de mensaje renderizados: texto (listas numeradas como <ol>), opciones (píldoras; al clic se deshabilitan las anteriores), adjunto (accept jpg/png/pdf, ≤ 5 MB en cliente; MIME real en servidor), encuesta (cinco estrellas, opcionId calif_n), handoff (banner ámbar). El agente se pinta con etiqueta «Personal CTIC». Errores: 401 recrea sesión; 409 conversación cerrada; 429/5xx reintentar; fallo de red mensaje offline.

SSE es mejora progresiva para handoff. EventSource reconecta con backoff (2 s × intentos, tope 30 s). Si SSE no está disponible de forma persistente, el usuario sigue escribiendo por POST; los mensajes del agente aparecerán al reconectar. 28. Párrafos modelo para la tesis

28.1 Capítulo de implementación (marco y plan)

La implementación se realizó en seis iteraciones semanales, a partir del DRS y de los PRD. Se empleó arquitectura C4 y un modelo conversacional híbrido: máquinas de estado para registrar, consultar, escalar y encuestar, y un motor RAG con router de dos capas (reglas y, si procede, LLM) para las preguntas frecuentes. El backend se separó en chatbot-api y ticket-service (ADR-03), persistidos en MySQL 8, con el widget como único canal de usuario final y un panel para el personal del CTIC. La definición de terminado coincide con los criterios QA-01 a QA-11, verificados por una suite E2E automatizada. El LLM no ejecuta acciones transaccionales: solo clasifica intenciones de texto libre y redacta respuestas ancladas a la base de conocimiento institucional.

28.2 Arquitectura y stack

El sistema se despliega con Docker Compose detrás de Nginx, que es el único puerto público. chatbot-api orquesta el diálogo, el RAG (Chroma embebido y embeddings e5-small en CPU) y el handoff en tiempo real por SSE. ticket-service implementa los contratos API-01 a API-03 y API-06 del DRS y simula el sistema de tickets institucional, de modo que en producción basta con redirigir TICKETS_API_BASE_URL al backend PHP de la universidad. La autenticación del personal usa Argon2id y JWT en cookie HttpOnly de ocho horas, validada same-origin por ambos servicios.

28.3 Resultados técnicos (para contrastar con el pre/post-test de usuarios)

En condiciones de laboratorio, con 50 sesiones concurrentes directas al servicio conversacional, la latencia p95 fue de 65 ms y no se observaron errores 5xx, lo que cumple REN-01 y QA-09 con holgura. El recall@1 del recuperador semántico sobre 32 preguntas de la base de conocimiento fue 96,9 %. La precisión de la capa de reglas del router, sin LLM, fue 88,2 % sobre 144 frases, 1,8 puntos bajo el objetivo del 90 % previsto para el clasificador de dos capas; los errores no derivaron a acciones transaccionales incorrectas. Estos indicadores instrumentan el capítulo de resultados junto con la tasa de autoservicio, la latencia percibida y la calificación 1–5 del pre-test y del post-test con usuarios reales.

28.4 Limitaciones que conviene declarar

El sistema no atiende segundo ni tercer nivel, no interpreta adjuntos ni voz, opera solo en español y solo en el dominio CTIC. El ticket-service es una simulación de contrato, no el sistema PHP de producción. Sin clave Anthropic el clasificador de capa 2 y la redacción LLM no operan; el servicio permanece útil. El SSE es de un solo worker. El umbral RAG 0,83 está calibrado para e5-small y debe recalibrarse si cambia el modelo. Los artículos iniciales de la KB son provisionales hasta la validación del CTIC.
